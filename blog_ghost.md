# An autoresearch loop moves at the speed of its slowest fork

Halfway through our BRIGHT experiments, we needed to test whether per-document **concept sketches** — short LLM-generated abstracts of each document, designed to bridge the vocabulary gap between user queries and formal technical writing — would close the retrieval gap on the robotics corpus. The change was non-trivial: a new column on a 62k-row table, two new indexes, generating sketches through Claude Haiku over ~6 hours, then re-running the eval to see if the paired statistics moved.

On most Postgres setups, this is a half-day of work plus a careful rollback plan if it loses. On [Ghost](https://ghost.build), it was four steps:

1. Fork the active database (~90 seconds).
2. Run the migration and the tagging job against the fork.
3. Evaluate.
4. Point `DATABASE_URL` at the winner; pause the loser.

The sketches experiment won (+0.054 nDCG@10, p=0.014 on paired sign test). We switched to the new fork and paused the old one. If sketches had regressed, we would have paused the *new* fork instead, kept the old one, and lost nothing but the tagging cost.

Over the course of the project we ran 30+ experiments at this cadence. Most regressed. We threw them away. We didn't have to care.

This post is about what that loop produced — and, more importantly, what it needed from the database to be tractable in the first place. The methodology is generic to any Postgres. The cadence isn't.

## What the loop needed from the data layer

Disciplined autoresearch needs four things from whatever stores your state.

**Fork-and-revert in minutes, not hours.** A loop where each experiment costs a half-day collapses to one experiment per day in practice — and at one experiment per day, you stop running the speculative ones. Most of our 30+ experiments were speculative, and most regressed. The value of the loop isn't in the wins; it's in being able to afford 20 losses to find 2 wins.

**Pause losers; don't delete them.** A regressed experiment isn't worthless. Two months in we wanted to compare an idea against a dead-end variant — *did we ever try this with sketches generated by Sonnet instead of Haiku?* — and the paused fork still had the answer. Deleting losers is the equivalent of throwing away the negative results in a research notebook.

**Per-fork billing that scales with use, not with existence.** If a paused fork costs $30/month to keep around, you delete it. If it costs storage only, you keep it. Whether you keep your dead-ends is what determines whether the loop accumulates institutional memory or just chases the current frontier.

**Share links so an agent's work is portable.** Several experiments were run by Claude in an agentic loop where the agent forked the DB, did schema work, and reported back. The share link meant we could open the agent's fork, verify, and either promote or discard. Without that, the agent's database state is a black box.

These four affordances are what made the loop tractable. Ghost happened to provide all four — fork creation in ~90 seconds, paused forks billed at storage only, query time billed in 15-minute increments, share links to forkable snapshots. If you're building a similar workflow on a stack that gives you these affordances, the rest of this post should transfer. If you're not, the loop's cadence will not survive contact with reality.

## The loop, briefly

Five rules, applied to every change:

1. Start from a named failure pattern. Look at queries where retrieval or answer quality was bad. Don't propose changes until the pattern has a name.
2. State the hypothesis explicitly. *If we do X, recall should move because Y.* If you can't state it, you don't understand the failure yet.
3. Implement the smallest change that tests the hypothesis. Not a refactor. One variable.
4. Run the eval. Compute paired statistics — paired t-test *and* sign test on per-query deltas. Disagreement between them is informative.
5. Adopted, reverted, or non-viable. Three attempts per hypothesis; if all three regress, declare non-viable. Either way, log it.

The log is the loop's primary output. The kept changes matter, but the rejected changes matter as much — they're how future iterations avoid retrying ideas that already failed.

## A case study: when sketches won, and how cheaply we tried

The robotics corpus on BRIGHT is a vocabulary trap. Queries are stuck-developer phrasings ("subscriber in hardware interface"); gold is canonical API documentation (`TopicBasedSystem`, `ApproximateTimeSynchronizer`). Hybrid search with raw queries caps out at retrieval recall ~0.335 on this corpus regardless of how clever the agent is downstream. The ceiling is corpus-side.

We hypothesized that a per-document **concept sketch** — an 80–120-word abstract written to contain both the canonical vocabulary *and* the stuck-developer phrasing — would let symptom-shaped queries hit the sketch indexes and surface the right document. The agent would then read the actual content and reason normally.

The mechanics:

- New `sketch` column on `bright_robotics`.
- New BM25 index and HNSW index on the sketch column.
- MCP server detects the new column at startup and switches from 2-way RRF (content BM25 + content semantic) to 4-way RRF (adds sketch BM25 + sketch semantic).
- Generate sketches for every document by passing the content through Claude Haiku with a prompt designed to produce the bridging vocabulary.

All of this happened on a fork:

```
mcp__ghost__ghost_fork(
  id="<previous-active>",
  name="bright-h7-sketches",
  wait=true
)
```

The fork came up in about 90 seconds. We ran the column migration, the index builds, and the tagging job (62k documents × Haiku, resumable across rate-limit windows, ~6 hours of wall time) against the fork. Throughout, the previous active database stayed untouched — other experiments could and did run against it in parallel.

The result on 101 robotics queries:

| Metric | Before | After | Δ |
|---|---:|---:|---:|
| nDCG@10 | 0.458 | 0.512 | +0.054 |
| Retrieval recall | 0.527 | 0.594 | +0.067 (sign-test p=0.014) |
| Ranking recall | 0.480 | 0.520 | +0.040 |

The paired statistics agreed: real signal, retrieval-recall driven, exactly the bottleneck the sketches were designed to break. We promoted the new fork to active and paused the old one. The old fork is still there — paused, billing storage only, resumable in seconds if we ever want to A/B against it again.

Two weeks later, we hypothesized that a different sketch-generation prompt (more emphasis on user-symptom phrasing) might push the recall further. We forked again, regenerated sketches with the new prompt, evaluated. It washed. We paused that fork too. The original sketches stayed live.

The whole sequence cost us less than a developer-day of human attention plus the LLM tagging budget. Without the fork-and-pause workflow, the second experiment — the one that lost — is the kind of thing we would not have run. Not running it means not knowing whether the win could have been bigger.

## What Ghost didn't do

The loop's substantive output — what to change, what to leave alone, how to read the paired statistics — is independent of any database. The autoresearch methodology will work on stock Postgres, on RDS, on Neon, on a self-hosted instance. We don't claim Ghost made the experiments succeed.

What Ghost did was lower the friction of attempting them. The kept experiments were the same ones we would have eventually kept. The *rejected* experiments — most of them — are the ones we would not have run at all if each one cost a half-day.

Concretely: we tried answer-first prompting, search hints in the tool description, sub-question decomposition, auto-hybrid forcing, more candidates per call. Every single one regressed. Most teams would never run those experiments to begin with, because the cost of confirming they regress isn't worth the small chance they help. The fork loop made it worth it. The systematic finding — *every help-the-model intervention regressed on Haiku-with-hybrid-search on MuSiQue* — is more useful than any individual win, and we only have it because we could afford to be wrong twenty times.

That's the load-bearing claim. The database is not what makes the loop *correct*. It's what makes the loop *affordable enough to keep running long enough to learn anything*.

## A limitation worth flagging

Forks are copy-on-write at the page level, which is fast for the initial clone but has consequences when the source fork has large HNSW indexes. The first few queries against a freshly forked database that touches a 100k+ row HNSW index pay a warming cost — pages have to fault in from the shared base. We hit this on the 121k-doc earth_science corpus: the first 5–10 eval queries on a fresh fork were noticeably slower than steady-state.

Workaround: warm the indexes with a few canned queries before starting timed evals. Not a dealbreaker, and steady-state behavior matches a non-forked instance, but worth knowing if you care about first-query latency.

## What we built, briefly

The autoresearch loop produced two classes of BRIGHT-shaped wins:

- **Per-domain prompts** that describe what gold *looks like* in each corpus, with concrete examples drawn from the corpus and explicit guidance on what to *avoid* searching for. These were the largest wins — up to +0.247 nDCG@10 on pony, +0.152 on leetcode, +0.137 on biology, all at p < 0.001.
- **Per-doc concept sketches** on the two corpora (robotics, aops) where retrieval was vocabulary-bottlenecked.

On MuSiQue, the loop's verdict was the opposite: every retrieval-side or prompt-side change we tried regressed. With 86.5% retrieval recall, the system is retrieval-saturated; the remaining gap is reasoning. The loop correctly identified that further retrieval work wouldn't help and stopped us from shipping speculative complexity.

The system places competitively on the public BRIGHT leaderboard against systems that fine-tune their retrievers — we use off-the-shelf OpenAI embeddings and off-the-shelf Claude, with no task-specific training. Full numbers, paired statistics on every adopted and rejected change, and the per-domain methodology are in the [companion research write-up](./blog.md). The point of *this* post is the cadence, not the score.

## What we want Ghost to be

The shape of an AI-assisted development session changes when a fresh, realistic database fork is one API call away. You stop scoping work around what your current schema and seed data can support. You start scoping it around what you can actually try — let the agent fork, mutate, evaluate, hand back a share link, move on.

We built Ghost because we wanted that for ourselves on workloads exactly like this one. It turns out the database is a surprisingly large part of what makes a tight change-and-test loop work or not work, and a surprisingly underserved one. If you're running this kind of loop — or want to — Ghost has a generous free tier; spin one up and try forking something.
